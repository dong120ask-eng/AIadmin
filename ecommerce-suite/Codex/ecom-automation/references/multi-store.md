# 多平台、多店铺、混合经营迭代验收 v5

## 修正结果

1. 原适配器只核店铺ID：增加tenant_id、platform、store_id联合响应核验，并要求店铺注册绑定。
2. 原去重键含task_id：移除展示编号，按业务动作、对象、前后值、operation_version去重；修改显示编号不再触发重复写。确需新的业务变更须确认前值，使用新operation_version，不用它绕过未决任务对账。
3. 原对象授权为全局列表：改为targets_by_store，并将授权bindings与当前店铺租户/平台绑定比对，旧授权配置默认阻塞。
4. 增加容量估算：人工分钟=日常人工分钟+订单量×异常率×每异常处理分钟；另核执行资源与接口配额。无实测数据时仅为情景估计。

## 混合经营档案

每店铺按租户、平台、店铺唯一登记，凭据隔离；每SKU记录经营模式、货权、供应商、结算和售后责任。支持自有库存、代发、寄售、服务及混合模式档案。档案不等于这些模式的后台执行器已实现。

- 自有库存：统一可售库存、预占与释放、仓库批次效期和补货资金。
- 代发：供应商可售核验、接单/拒单/发货回执、缺货替代授权、时效和售后责任。
- 寄售：货权、结算周期、佣金、退件及库存归属。
- 服务/定制：交付资源、需求确认、阶段验收和退款边界。
- 混合：逐SKU/订单路由，不把全店默认当所有商品模式；拆单、成本、发货和售后分别对账。

## 一人多店的实际控制面

统一异常待办：按影响金额、时效和客户风险排序，相同根因合并但保留各店事件。批量预览、店铺内串行、跨店受控并发须由队列服务实现；当前单机原型仍串行，不能把容量估计当已实现并发。

每租户、平台和店铺分别控制预算、配额、权限、停止开关、数据及日志。共享实体库存只允许明确货权和映射的店铺共用。活动报名和预算变更必须先有平台专用资格/资金校验，当前仍阻塞。

## 运行容量估算

`python Codex/ecom-automation/scripts/capacity.py --input Codex/ecom-automation/assets/capacity.example.json --output 新容量结果.json`

示例是合成情景，不是真实经营数据。按实际订单、异常率、人工耗时、API配额和资源更新。先单店，再少量同平台店，再跨平台混合经营；每阶段验证峰值处理延迟、人工待办、漏单/重复动作、超卖、预算及利润。达到约定阈值才扩容，不承诺无限店铺。
